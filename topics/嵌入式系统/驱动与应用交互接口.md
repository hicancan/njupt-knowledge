# 用户空间应用程序通过open/read/write/ioctl与底层驱动交互的接口实现

## 用户空间如何“碰”到内核驱动

嵌入式 Linux 里，硬件设备由**内核驱动**管理。用户空间的应用程序不能直接读写物理寄存器，必须通过**设备文件**这一层“门”来间接操作。`/dev/led` 就是这样一个设备文件：它在文件系统里看起来像普通文件，但背后连接的是 LED 驱动。

```mermaid
flowchart LR
    A["Qt 应用程序"] -->|"open/read/write/ioctl"| B["/dev/led 设备文件"]
    B -->|"系统调用"| C["内核 LED 驱动"]
    C -->|"GPIO 寄存器"| D["物理 LED"]
```

> [!IMPORTANT]
> 设备文件是用户空间与内核驱动的**唯一合法接口**。应用层代码里出现的 `fd` 就是 `open("/dev/led", ...)` 返回的**文件描述符**，后续一切操作都围绕它进行。

## 四个系统调用各自干什么

| 函数 | 作用 | 在 LED 场景中的用途 |
|---|---|---|
| `open()` | 获取设备访问权，返回 `fd` | 打开 `/dev/led` |
| `write()` | 向设备写数据 | 若驱动支持，可写亮度值 |
| `read()` | 从设备读数据 | 若驱动支持，可读当前状态 |
| `ioctl()` | “万能控制通道”，传命令码 | 发送 `LEDON` / `LEDOFF` 命令 |

这个场景里，LED 只有开和关两种状态，不需要传递数值数据，所以最合适的是 `ioctl()`——它只传一个**命令码**（`LEDON` 或 `LEDOFF`）下去，驱动收到命令后去翻 GPIO 寄存器。

> [!NOTE]
> 为什么不用 `write()`？`write()` 适合持续的数据流（比如串口），而开关灯本质是**离散命令**。用 `ioctl` 语义更清晰，也是课件里驱动给好的接口。

## Qt 按钮的实现

题干假设 Qt 界面里已经放好了两个按钮，对象名分别是 `m_on` 和 `m_off`。最标准的做法是**在构造函数里连接信号与槽**：

```cpp
// 构造函数中
connect(m_on,  SIGNAL(clicked()), this, SLOT(onLedOn()));
connect(m_off, SIGNAL(clicked()), this, SLOT(onLedOff()));
```

然后槽函数里做四步：打开设备 → 发命令 → 判错 → 关闭设备。

```cpp
void MyWidget::onLedOn()
{
    int fd = ::open("/dev/led", O_RDWR);
    if (fd < 0) { /* 打开失败，弹提示 */ return; }

    ::ioctl(fd, LEDON);

    ::close(fd);
}

void MyWidget::onLedOff()
{
    int fd = ::open("/dev/led", O_RDWR);
    if (fd < 0) { /* 打开失败，弹提示 */ return; }

    ::ioctl(fd, LEDOFF);

    ::close(fd);
}
```

> [!TIP]
> **开-控-关**三步走是设备操作的固定套路：先 `open` 拿 `fd`，再做业务操作，最后 `close` 释放。忘写 `close` 会导致文件描述符泄漏，嵌入式系统资源紧张，这很致命。

## 容易踩的三个坑

**坑一：`::open` 而不是 `open`。** Qt 的 `QFile` 有自己的 `open` 方法，如果在 Qt 类内部直接写 `open(...)`，编译器可能解析成 `QFile::open`，导致类型不匹配。前面加 `::` 表示调用**全局 C 库的 `open`**。

**坑二：命令码作用域。** `LEDON` 和 `LEDOFF` 通常定义在驱动的头文件里（如 `led_drv.h`），Qt 工程必须 `#include` 该头文件，否则编译报“未定义标识符”。

**坑三：忘了检查 `fd`。** 如果驱动没有加载或者权限不够，`open` 返回 `-1`，此时直接调用 `ioctl(-1, LEDON)` 是未定义行为。==每次 `open` 后必须判 `fd < 0` 再决定是否继续。==

## 一个“算对了”的完整例子

考试设计题如果要求更完整，可以这样写（含构造函数和两个槽函数）：

```cpp
// ledwidget.h
class LedWidget : public QWidget
{
    Q_OBJECT
public:
    LedWidget(QWidget *parent = nullptr);
private slots:
    void onLedOn();
    void onLedOff();
};

// ledwidget.cpp
LedWidget::LedWidget(QWidget *parent) : QWidget(parent)
{
    connect(m_on,  SIGNAL(clicked()), this, SLOT(onLedOn()));
    connect(m_off, SIGNAL(clicked()), this, SLOT(onLedOff()));
}

void LedWidget::onLedOn()
{
    int fd = ::open("/dev/led", O_RDWR);
    if (fd < 0) return;
    ::ioctl(fd, LEDON);
    ::close(fd);
}

void LedWidget::onLedOff()
{
    int fd = ::open("/dev/led", O_RDWR);
    if (fd < 0) return;
    ::ioctl(fd, LEDOFF);
    ::close(fd);
}
```

> [!WARNING]
> 阅卷时特别看两处：**有没有判 `fd < 0`**，**有没有 `close(fd)`**。缺少任何一个都是扣分点，因为这两条直接反映学生是否真正理解“设备文件生命周期”。

---

**一句话总结**：`open` 拿钥匙，`ioctl` 发命令，`close` 还钥匙；Qt 只是把它们包进按钮的槽函数里，底层逻辑和命令行 C 程序完全一样。
