# 主机字节序与网络字节序及其转换

## 为什么需要字节序转换

不同 CPU 在内存中存放多字节整数的方式不同：**大端序（big-endian）**把最高有效字节放在低地址，**小端序（little-endian）**把最低有效字节放在低地址。而网络协议要求统一格式，因此 TCP/IP 规定多字节字段一律采用==网络字节序，即大端序==。

发送方必须把本机使用的**主机字节序**转换为网络字节序；接收方则反向转换，否则同一个 16 位或 32 位字段可能被解释成完全不同的数值。

| 转换方向 | 16 位函数 | 32 位函数 | 名称含义 |
|---|---|---|---|
| 主机 → 网络 | `htons()` | `htonl()` | host to network |
| 网络 → 主机 | `ntohs()` | `ntohl()` | network to host |

其中 `s` 表示 short，`l` 表示 long。若主机本身就是大端序，这些函数可以不做实际交换；若是小端序，则交换字节。

```mermaid
flowchart LR
    A["主机整数"] --> B["hton 转换"]
    B --> C["网络字节序"]
    C --> D["ntoh 转换"]
    D --> E["主机整数"]
```

## 一个算对的例子

假设 16 位字段的十进制值为 `258`，写成十六进制是 `0x0102`。

- 小端主机内存：`02 01`
- 调用 `htons(258)` 后，网络中发送：`01 02`
- 接收端调用 `ntohs()`，恢复为主机整数 `258`

注意，转换的是**整数的解释方式**，不是把十进制数字倒过来，也不是每个字节内部翻转比特。

## IP 分片偏移为什么不用转换

`ip_forward` 在调用 `icmp_error` 前，会把分片 ID 从主机字节序转换为网络字节序，却不转换分片偏移量。关键问题是：**这个 ICMP 差错报文可能针对哪个分片？**

ICMP 差错报文只针对 IP 数据报的==初始分片==生成，而初始分片的 `fragment offset` 恒为 $0$。无论 16 位字段按大端还是小端存放，其字节都是：

$$
0 \longrightarrow \texttt{00 00}
$$

所以偏移量的主机字节序形式与网络字节序形式完全相同，不转换也不会产生错误。

> [!IMPORTANT]
> 这里“不转换也正确”只适用于初始分片偏移量必为 $0$ 的特殊情况，不能推广为“IP 字段都不用转换”。

> [!WARNING]
> 不要混淆 `fragment offset` 与 `total length`。偏移量为 $0$ 时交换字节结果不变；长度通常不是 $0$，若字节序错误，解释出的数值一般会改变。题目若只问 IP offset，应答“只处理初始分片，且其偏移恒为零”。

## 常见误区与解题技巧

- **字节序不等于位序**：`htons()` 处理多字节整数的字节排列，不翻转单个字节内的比特。
- **单字节字段无需转换**：如 8 位整数不存在字节排列歧义。
- **结构体不能整体盲目转换**：应按字段宽度分别处理，并考虑协议规定的字段含义。
- **“首片”不是“所有分片”**：首片偏移为 $0$，后续分片偏移通常非零，不能套用同一结论。

> [!TIP]
> 简答题可压缩成一句：**ICMP error 只针对初始分片，初始分片 offset 恒为 0，而 0 在两种字节序下表示相同，因此无需转换。**
