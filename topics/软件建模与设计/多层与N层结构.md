# 多层/N层体系结构与B/S架构

## 从单层到多层：为什么要分层

最早的客户端/服务器（C/S）是两层结构：客户端负责界面与业务逻辑，服务器负责数据存储。随着系统变大，两个问题暴露出来：

- **客户端太“胖”**：业务规则散落在每个客户端里，改一条规则要重新部署所有客户端。
- **服务器被绑死**：数据库结构一变，所有客户端都要跟着改。

于是把中间的业务逻辑抽出来，形成中间层，这就是多层（N 层）体系结构的动机。

> [!NOTE]
> 两层 C/S 中，胖客户端直接访问数据库；三层结构中，客户端只做表示层，业务逻辑集中在中间层。

```mermaid
flowchart LR
    A["客户端层（表示）"] --> B["中间层（业务逻辑）"] --> C["数据层（数据库）"]
```

## 各层职责与“既是客户端又是服务层”

三层体系结构最基本的划分如下：

| 层 | 职责 | 典型技术 |
|---|---|---|
| 客户端层 | 界面展示、接收输入 | 浏览器、桌面程序 |
| 中间层（业务逻辑层） | 校验、计算、事务控制 | 应用服务器（如 Tomcat、WebLogic） |
| 数据层 | 持久化存储与查询 | 数据库（如 MySQL） |

关键点在于中间层的==双重身份==：它向数据层发起请求时扮演客户端，接收客户端层请求并提供服务时扮演服务层。所以考题中“中间层既是客户端层也是服务层”是正确的。

> [!IMPORTANT]
> 中间层对上是服务层，对下是客户端层。这个双重角色是多层结构里最容易考的概念。

## B/S 架构：一种特殊的三层 C/S

B/S（Browser/Server）架构是多层 C/S 的一种典型实现形式：

- **Browser** 取代专用客户端程序，承担表示层；
- **Web 服务器 / 应用服务器**承担业务逻辑层；
- **数据库服务器**承担数据层。

```mermaid
flowchart LR
    A["浏览器"] -->|HTTP 请求| B["Web/应用服务器"] -->|SQL| C["数据库"]
    C -->|结果集| B -->|HTML/JSON| A
```

B/S 相比传统 C/S 的**优点**是客户端零维护、跨平台；**代价**是交互能力受限于浏览器，复杂图形操作（如 CAD）不如专用客户端灵活。

## 常见误区

> [!WARNING]
> 多层 ≠ 部署在多台机器。三层逻辑可以全在一台服务器上运行，分层讲的是**逻辑职责**，不是物理分布。

> [!CAUTION]
> 不要认为“中间层只做转发”。中间层承载核心业务规则与事务协调，是整个系统的重心。

## 算对了的例子

**题目**：一个多层客户端/服务器体系结构模式中，以下哪个关于中间层的描述是正确的？

- A. 中间层是客户端层
- B. 中间层是服务层
- C. 中间层既是控制层也是服务层
- D. 中间层既是客户端层也是服务层

**分析**：

以“浏览器下单”为例。浏览器向 Web 服务器发送订单请求，此时 Web 服务器是==服务层==；Web 服务器处理业务后向数据库查询库存，此时它又是==客户端层==。中间层同时具备两种角色。

**答案**：D

> [!TIP]
> 看到“中间层”就画一条三角链：谁请求我，我就是服务层；我请求谁，我就是客户端层。
