# 活锁与死锁（死锁预防、诊断与解除）

在并发控制中，事务等待锁是常态，但如果等待变成了“永远”，系统就出了问题。这种“永远等待”一定都是死锁吗？其实不然，我们需要区分两种截然不同的异常状态：活锁与死锁。

## 活锁：忙而无功的等待

想象一个场景：事务 $T_1$ 请求对数据对象 $R$ 加锁，但 $R$ 已被 $T_2$ 占用；当 $T_2$ 释放锁后，系统又优先批准了后来的 $T_3$、$T_4$……$T_1$ 始终得不到服务。这就是==活锁==。

> [!IMPORTANT]
> 活锁的本质是**调度策略不公平**。事务并未陷入循环等待，而是因优先级或随机调度被持续“插队”，导致永远处于等待状态。

解决活锁的方法非常直接：采用==先来先服务（FCFS）==策略。系统严格按请求时间戳排序授权，确保每个事务最终都能获得锁，从根本上消除饥饿现象。

## 死锁：互相等待的死局

如果 $T_1$ 持有 $R_1$ 并等待 $R_2$，同时 $T_2$ 持有 $R_2$ 并等待 $R_1$，两者都无法继续推进，这便是==死锁==。

```mermaid
flowchart LR
    T1["T1 持 R1"] -->|等待 R2| T2["T2 持 R2"]
    T2 -->|等待 R1| T1
```

### 预防还是解除？

操作系统常通过破坏必要条件来预防死锁，但在数据库中这往往代价过高。例如“一次封锁法”要求事务启动时锁定所有数据，虽能防死锁，却严重降低并发度。而==两段锁协议（2PL）== 虽保证可串行化，但因允许分阶段加锁，仍可能发生死锁。

> [!WARNING]
> 遵守两段锁协议 $\neq$ 不会发生死锁。2PL 仅保证调度的正确性，不保证不死锁。

因此，数据库更普遍采用==诊断并解除==的策略：

- **超时法**：事务等待超过时限即判定死锁。简单但可能误判（长事务被冤枉）或漏判（时限过长）。
- **等待图法**：并发子系统周期性生成事务等待图，若检测到==回路==则确认死锁。这是更精确的诊断方法。

解除死锁时，系统选择一个==处理代价最小==的事务进行撤销（回滚），释放其持有的锁，打破循环等待链。

## 活锁 vs 死锁：关键辨析

| 对比维度 | 活锁 | 死锁 |
| :--- | :--- | :--- |
| 等待性质 | 非循环，被持续抢占 | 循环等待，形成闭环 |
| 根本原因 | 调度策略不公平 | 资源竞争+推进顺序不当 |
| 典型解法 | FCFS 排队 | 等待图检测 + 撤销事务 |
| 与2PL关系 | 无关 | 2PL下仍可能发生 |

> [!TIP]
> 考试中若问“两段锁协议能否防止死锁”，答案一定是**不能**。防止死锁需用一次封锁法或有序封锁法，而2PL只保证可串行化。

## 算对了的例子

设 $T_1$、$T_2$ 按以下顺序执行：

- $T_1$: Lock X(R1) → Lock X(R2)
- $T_2$: Lock X(R2) → Lock X(R1)

若 $T_1$ 成功锁住 R1，$T_2$ 成功锁住 R2，随后 $T_1$ 请求 R2 被阻塞，$T_2$ 请求 R1 也被阻塞，等待图中出现 $T_1 \to T_2 \to T_1$ 回路，==确认死锁==。此时系统比较两事务已执行的更新量，假设 $T_2$ 仅完成一条插入而 $T_1$ 已修改百条记录，则撤销 $T_2$，释放 R2，$T_1$ 得以继续。此例清晰展示了诊断与解除的完整流程。
