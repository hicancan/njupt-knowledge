# 逻辑结构设计（E-R图向关系模型的转换）

## 什么是逻辑结构设计

逻辑结构设计是把需求分析和概念结构设计的结果，转换成==目标数据库管理系统能够实现的数据结构==。当目标数据模型是关系模型时，核心任务就是：

> 将 E-R 图转换为关系模式，并确定各关系模式的主键、外键。

它位于概念结构设计与物理结构设计之间：

```mermaid
flowchart LR
    A["需求分析"] --> B["概念结构设计"]
    B --> C["E-R图"]
    C --> D["逻辑结构设计"]
    D --> E["关系模式集"]
    E --> F["物理结构设计"]
    F --> G["数据库实施"]
```

概念设计关注“现实世界中有哪些实体和联系”；逻辑设计则把这些信息落实为“数据库中有哪些表、哪些属性和引用关系”。

## 基本转换规则

### 实体集转换为关系模式

每个实体集转换成一个关系模式：

- 实体集的属性转换为关系的属性；
- 实体集的键转换为关系的主键；
- 可以根据实际需要重命名，但应保持名称一致。

例如“公司”实体转换为：

```text
公司（公司编号，公司名，地址）
```

其中公司编号是主键。

### 二元联系的转换

联系类型决定了外键放在哪里、是否需要新建关系。

| 联系类型 | 转换方法 | 关键点 |
|---|---|---|
| $1:1$ | 联系属性放入任一方，并在该方引用另一方主键 | 双方各保留一个外键会造成冗余 |
| $1:n$ | 联系属性放入 $n$ 方，$n$ 方引用 $1$ 方主键 | 外键放在“多”的一方 |
| $m:n$ | 联系单独转换为新关系，放入双方主键和联系属性 | 新关系的主键通常是双方主键的组合 |

> [!TIP]
> 记忆口诀：**一对一任选一方，一对多放在多方，多对多单独成表。**

## 示例：公司、仓库与职工

题目的联系如下：

- 公司与仓库是 $1:n$：一个公司管辖多个仓库，一个仓库只属于一个公司；
- 仓库与职工是 $1:n$：一个仓库聘用多个职工，一个职工只在一个仓库工作；
- “聘期、工资”是“聘用”联系的属性。

由此得到：

```text
公司（公司编号，公司名，地址）
仓库（仓库编号，仓库名，地址，公司编号）
职工（职工编号，姓名，性别，仓库编号，聘期，工资）
```

主键和外键为：

| 关系模式 | 主键 | 外键 |
|---|---|---|
| 公司 | 公司编号 | 无 |
| 仓库 | 仓库编号 | 公司编号 → 公司（公司编号） |
| 职工 | 职工编号 | 仓库编号 → 仓库（仓库编号） |

为什么“聘期、工资”放进职工表？因为每个职工只对应一个仓库，也就只对应一次聘用关系，所以这些联系属性可以并入 $n$ 方的职工关系。

> [!WARNING]
> 如果题目改成“一个职工可在多个仓库工作”，仓库与职工就成为 $m:n$，不能继续把外键直接放在职工表中，而应增加“聘用”关系。

## 多对多联系的例子

产品与门市部之间是 $m:n$，且“月销售量”属于“销售”联系，因此应新建销售关系：

```text
门市部（门市部号，门市部名，地址）
营业员（工号，姓名，性别，聘期，工资，门市部号）
产品（产品号，产品名，规格，单价）
销售（产品号，门市部号，月销售量）
```

其中：

- 销售的主键是（产品号，门市部号）；
- 产品号是外键，引用产品；
- 门市部号是外键，引用门市部；
- 营业员中的门市部号是外键，引用门市部，因为营业员与门市部是 $1:n$。

> [!IMPORTANT]
> 转换完成后不能只列出关系模式，还要明确指出：==每个关系模式的主键、外键及其被引用的关系==。

## 常见易错点

- **把联系属性放错位置**：$1:n$ 联系应放到 $n$ 方，$m:n$ 联系应单独建表。
- **多建关系**：每个实体一个关系并不意味着每个联系都要建关系。
- **漏掉联系属性**：如“聘期、工资”“月销售量”不能无故丢失。
- **主键选择错误**：$m:n$ 新关系通常以双方主键的组合作为主键。
- **外键方向错误**：外键位于 $n$ 方，并引用 $1$ 方的候选键或主键。
- **名称随意改写**：题干给定中文名称时，应沿用“公司、仓库、职工”等名称。

完成转换后，通常还要检查关系模式是否符合要求，并进行规范化处理，为后续物理设计和数据库实施做好准备。
