# 概念结构设计（E-R图设计、实体与联系、设计方法）

## 概念结构设计：从需求到E-R图

在数据库设计的六步法中，==概念结构设计是承上启下的关键阶段==。它将需求分析得到的数据字典、数据流图等“用户语言”，抽象为独立于具体DBMS的**信息结构（概念模型）**。为什么不直接进入逻辑设计？因为E-R图屏蔽了底层存储细节，专注于表达现实世界中“事物及其联系”，是后续转换为关系模式、验证需求完整性的唯一蓝图。

### 核心要素与绘图规范

E-R图由三个基本构件组成，绘图时需严格遵守南邮课件规范：

| 要素 | 图形符号 | 关键规则 |
| :--- | :--- | :--- |
| 实体型 | 矩形框 | 框内写实体名，码属性下划线 |
| 属性 | 椭圆形 | 无向边连实体，==码必须下划线== |
| 联系 | 菱形框 | 标明联系名，连线旁标注1:1/1:n/m:n |

> [!IMPORTANT]
> 联系也可以拥有属性！例如“学生”与“课程”的“选修”联系具有“成绩”属性，该属性必须连向菱形框“选修”，而非任一实体。

### 实体与属性的划分原则

这是设计中最易混淆的点。判断一个对象是实体还是属性，请问自己两个问题：它是否具有独立存在的意义？它是否与其他实体存在联系？

- **作为属性**：若“职称”仅用于描述教师，且不同职称无差异化福利，则它是“教师”的属性。
- **作为实体**：若“职称”关联了不同的工资标准、岗位津贴，或“专业”被多个学生辅修，则必须提升为独立实体。

> [!WARNING]
> 属性不能与其他实体发生联系。若发现某“属性”还连着别的实体，请立即将其升级为实体型。

### 联系类型的判定与转换铺垫

准确识别联系类型是后续逻辑设计的基础。请根据业务语义判断基数：

- **1:1**：班级与班长（一个班一个正班长，一个班长只在一个班）。
- **1:n**：班级与学生（一班多生，一生一班）。==外键未来放在n端==。
- **m:n**：学生与课程（多选多）。==必须转换为独立关系模式==。
- **多元联系**：三个及以上实体间的联系（如供应商-项目-零件），通常视为m:n处理。

### 局部E-R图集成与冗余消除

当系统较大时，需先设计分E-R图再集成。集成时重点解决三类冲突：

1.  **属性冲突**：同一对象在不同子图中属性个数或次序不同 → 取并集。
2.  **命名冲突**：同名异义或异名同义 → 统一术语。
3.  **结构冲突**：同一对象在一处是实体、另一处是属性 → 按语义统一抽象层次。

> [!TIP]
> 冗余检查可用函数依赖验证：若联系 $A \to B$ 可由其他联系导出（如系编号→学院编号已隐含在专业→系中），则该联系为冗余，应消除。但==为提高查询效率而保留的合理冗余除外==。

### 真题示例：商业集团E-R图设计

以历年综合题为例：商店、商品、职工三实体。商店与商品“销售”（m:n，含月销售量）；商店与职工“聘用”（1:n，含聘期、月薪）。

```mermaid
erDiagram
    STORE["商店"] {
        string 商店编号 PK
        string 商店名
        string 地址
    }
    PRODUCT["商品"] {
        string 商品编号 PK
        string 商品名
        float 单价
    }
    EMPLOYEE["职工"] {
        string 职工编号 PK
        string 姓名
        string 性别
    }
    STORE ||--o{ EMPLOYEE : "聘用(1:n)"
    STORE }|--|{ PRODUCT : "销售(m:n)"
    SALE["销售"] {
        int 月销售量
    }
    HIRE["聘用"] {
        date 聘期
        float 月薪
    }
    STORE ||--|| HIRE
    HIRE ||--o{ EMPLOYEE
    STORE }|--|| SALE
    SALE ||--|{ PRODUCT
```

> [!CAUTION]
> “聘用”是1:n联系，其属性“聘期、月薪”应归入n端“职工”关系模式中，而非单独建表。若误判为m:n而新建“聘用”表，将导致逻辑设计错误扣分。务必先审清基数再画图！
