# 封锁协议（一级、二级、三级封锁协议）

## 为什么需要封锁协议

事务并发执行可能产生三类不一致：

- **丢失修改**：两个事务读取并修改同一数据，后提交的修改覆盖先提交的修改。
- **读“脏”数据**：事务读到了另一事务尚未提交、随后可能被撤销的修改。
- **不可重复读**：同一事务两次读取同一数据，中间被其他事务修改，导致结果不同。

仅有 X 锁、S 锁还不够，还必须约定==何时加锁、何时释放锁==。这些规则称为**封锁协议**。协议级别越高，一致性保证越强，但锁持有时间通常越长，并发度可能降低。

## 三级封锁协议

| 协议 | 加锁与释放规则 | 能防止的问题 | 仍可能出现 |
|---|---|---|---|
| 一级 | 修改数据前加 X 锁，**事务结束**才释放；只读可不加锁 | 丢失修改 | 读“脏”数据、不可重复读 |
| 二级 | 在一级基础上，读数据前加 S 锁，**读完即可释放** | 丢失修改、读“脏”数据 | 不可重复读 |
| 三级 | 在一级基础上，读数据前加 S 锁，**事务结束才释放** | 丢失修改、读“脏”数据、不可重复读 | 本表三类问题均可防止 |

> [!IMPORTANT]
> 三级协议都规定：写前加 X 锁，并保持到事务结束。二级与三级的关键区别只在 S 锁：==二级“读完放”，三级“结束放”==。

### 一级：为什么能防止丢失修改

事务 $T_1$ 修改 $R$ 前获得 X 锁并保持到结束，事务 $T_2$ 若想修改 $R$，必须等待。因此 $T_1$ 的修改不会在尚未结束时被 $T_2$ 覆盖。

但只读事务可以不加 S 锁，所以仍可能读到未提交修改，也无法保证两次读取结果相同。

### 二级：为什么能防止读“脏”数据

读前必须加 S 锁。若另一事务正在修改该数据，它持有 X 锁；由于 S 锁与 X 锁不相容，读事务必须等待，直到修改事务结束，因此不会读到其未提交的修改。

然而，S 锁读完就释放，其他事务随后可以修改该数据，所以仍可能不可重复读。

### 三级：为什么能保证可重复读

S 锁一直保持到事务结束。在第一次读到事务结束期间，其他事务不能获得该数据的 X 锁，因而不能修改它，再次读取时结果保持一致。

```mermaid
flowchart LR
    A["一级：写前X锁"] --> B["防丢失修改"]
    B --> C["二级：读前S锁"]
    C --> D["读完释放S锁"]
    D --> E["再防读脏数据"]
    E --> F["三级：S锁到结束"]
    F --> G["再防不可重复读"]
```

## 一个正确的判断例子

设事务 $T$ 两次读取数据 $R$，期间事务 $T_1$ 修改并提交了 $R$。

- 若采用**二级封锁协议**：$T$ 第一次读完 $R$ 后释放 S 锁，$T_1$ 可获得 X 锁并修改 $R$；$T$ 第二次读取可能得到新值，因此可能出现不可重复读。
- 若采用**三级封锁协议**：$T$ 的 S 锁保持到事务结束，$T_1$ 必须等待，不能在 $T$ 两次读取之间修改 $R$，因此可重复读。

> [!WARNING]
> “读完即可释放”不是指事务结束，而是指本次读操作完成。也不要把“三级协议解决三类不一致”误记成“三级协议保证调度可串行化”；可串行化还需结合两段锁协议等知识判断。

> [!TIP]
> 按锁的持有时间记忆：**X 锁都到事务结束；S 锁一级没有、二级短、三级长。** 一致性保证则逐级累加：一级防丢失修改，二级再防读“脏”数据，三级再防不可重复读。
