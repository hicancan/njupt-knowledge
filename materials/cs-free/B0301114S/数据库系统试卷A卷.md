## 五、实验及现象分析（10 分）

### 实验及现象分析 1

设 U1（口令 p1）和 U2（口令 p2）是 Oracle 的合法用户，拥有 connect 和 resource 特权；U1 是第三题中 3 个基表的拥有者。写出下列操作的含义：

(1) `SQLPLUS> connect U1/p1;`

(2) `SQLPLUS> grant update(库存量) on 图书 to U2;`

(3) `SQLPLUS> set auto off;`

(4) `SQLPLUS> update 图书 set 库存量=库存量+10;`

(5) `SQLPLUS> rollback;`

参考解答：**结论**

1.  **建立连接**：以用户 U1 的身份登录 Oracle 数据库。
2.  **授予权限**：将“图书”表中“库存量”列的更新权限授予用户 U2。
3.  **关闭自动提交**：设置当前会话不自动提交事务，需手动控制事务边界。
4.  **执行更新**：将“图书”表中所有记录的“库存量”字段值增加 10（此时修改仅在内存/Undo段中，未持久化）。
5.  **回滚事务**：撤销第 (4) 步所做的所有修改，使数据恢复到修改前的状态。

**推理与分析过程**

1.  `connect U1/p1` 是 SQL*Plus 的标准连接命令。`U1` 为用户名，`p1` 为口令。该操作建立客户端与数据库服务器之间的会话，后续操作均以 U1 的身份和权限执行。
2.  `grant update(库存量) on 图书 to U2` 是 DCL（数据控制语言）语句。
    *   `update(库存量)`：指定了细粒度的列级权限，仅允许修改“库存量”这一列，而非整行或整表。
    *   `on 图书`：指定作用对象为 U1 拥有的“图书”基表。
    *   `to U2`：指定被授权者为用户 U2。
3.  `set auto off` 是 SQL*Plus 的环境变量设置命令。
    *   `auto` 指 `autocommit`。
    *   `off` 表示关闭自动提交功能。在 Oracle 中，默认情况下 DML 操作不会自动提交，但某些客户端工具默认开启自动提交。此命令确保后续的 DML 操作（如 UPDATE）处于一个显式的事务中，直到遇到 `COMMIT` 或 `ROLLBACK`。
4.  `update 图书 set 库存量=库存量+10` 是 DML（数据操纵语言）语句。
    *   由于没有 `WHERE` 子句，该操作作用于“图书”表的**所有行**。
    *   逻辑上是将每本书的库存量在原值基础上加 10。
    *   结合步骤 (3)，此修改属于当前未提交事务的一部分，其他用户暂时看不到此变化（取决于隔离级别，通常读不到未提交数据），且数据尚未写入数据文件。
5.  `rollback` 是事务控制语句。
    *   它结束当前事务，并撤销自上一个 `COMMIT` 或 `ROLLBACK` 以来所做的所有 DML 更改。
    *   因此，步骤 (4) 中对“图书”表库存量的增加操作被完全取消，数据恢复原状。

参考解答：## 结论

这是一个典型的 **多事务并发 + 行级锁 + 写锁阻塞** 现象。U1 先修改未提交，持有写锁；U2 的更新会被阻塞，直到 U1 提交后 U2 才能继续。由于两次更新都是对所有图书进行 $+10$ 与 $-10$，最终总效果相互抵消，因此最终数据库库存量与最初相比 **无变化**。

## (1)

**现象：**

U1 成功执行更新，提示类似：

```text
已更新 N 行。
```

此时 U1 修改了所有图书的库存量，使：

$$
\text{库存量} \leftarrow \text{库存量} + 10
$$

但 **尚未提交**，因此其他用户还看不到该修改，U1 持有这些行的排他锁（写锁）。

---

## (2)

**现象：**

U2 执行：

```sql
update 图书 set 库存量=库存量-10;
```

后出现 **阻塞（等待）**，SQLPLUS 光标停住，不返回“已更新”信息，直到 U1 结束事务。

**原因：**

U1 已经对这些行执行了 `update` 但未 `commit`，因此持有排他锁（X 锁）。  
U2 也要更新同样的行，需要获得排他锁，但排他锁之间不兼容，所以 U2 必须等待 U1 释放锁。

---

## (3)

**现象：**

U1 执行：

```sql
commit;
```

提示类似：

```text
提交完成。
```

U1 的更新永久生效，并释放其持有的排他锁。

**原因：**

`commit` 会结束 U1 的事务，使其更新持久化，同时释放锁资源。  
U2 之前被阻塞的更新请求随后可以获得锁并继续执行，通常会显示更新成功。

---

## (4)

**结果：**

数据库中基表图书的库存量 **无变化**。

**原因：**

设某图书原库存量为 $x$。

U1 提交后使库存量变为：

$$
x+10
$$

U2 提交后在此基础上执行：

$$
(x+10)-10=x
$$

因此对每一行都有：

$$
\text{最终库存量}=\text{原库存量}
$$

所以最终库存量与最初相比无变化。
