### 简明推理

题目要求“删除基本表 **Score**，同时删除参照该表的约束及基于该表的视图”，这意味着：
- 需要 DDL 语句（删除表结构），而非 DML（只删数据）。
- 必须指定级联删除依赖对象（外键约束、视图等）。

逐个分析选项：

- **A. `DELETE TABLE Score;`**  
  无此语法，`DELETE` 只能删除数据行，不能删表结构。❌

- **B. `DROP TABLE Score;`**  
  可以删除表结构，但缺少 `CASCADE` 时，若有外键或视图依赖会失败，不会自动删除相关约束和视图。❌

- **C. `DELETE TABLE Score CASCADE;`**  
  语法错误，`DELETE` 不支持 `CASCADE` 子句。❌

- **D. `DROP TABLE Score CASCADE;`**  
  删除表结构，`CASCADE` 自动删除依赖在此表上的外键约束和视图，完全符合题意。✅

---

因此选项 **D** 正确。

该 SQL 查询不能正确实现"查询没有选修 1 号课程的学生姓名"这一需求。

## 推理

**关键问题：子查询中 `Student.Sno` 的引用方式。**

在子查询：

```sql
SELECT * FROM SC 
WHERE Grade < 60 AND SC.Sno = Student.Sno
```

中，`Student.Sno` 是**相关子查询**（correlated subquery）的写法，它依赖于外层 `Student` 表的当前行。这意味着整个 `NOT EXISTS` 判断的是：

> "对于当前学生，**不存在**一门成绩低于 60 分且该学生选修了的课程。"

即"该学生所有选修课程的成绩都不低于 60 分"（或该学生没有选修任何课程），**而非**"该学生没有选修 1 号课程"。

**正确写法**应将 1 号课程的条件放入子查询，并去掉与外层表的相关性：

```sql
SELECT Sname 
FROM Student 
WHERE NOT EXISTS (
    SELECT * FROM SC 
    WHERE SC.Sno = Student.Sno AND SC.Cno = '1'
);
```

这样 `NOT EXISTS` 判断的才是"不存在该学生选修 1 号课程的记录"。

### 1. 分组过滤（HAVING 的使用）

**题目意图**：找出每个部门（Dept）中平均工资（Salary）大于 $3000$ 的部门。

**参考解答**：
$$
\texttt{SELECT Dept, AVG(Salary) FROM Staff GROUP BY Dept HAVING AVG(Salary) > 3000}
$$

**推理**：
1.  需要按部门统计，故使用 `GROUP BY Dept`。
2.  过滤的是“组”的属性（平均值），而非单行属性，故必须使用 `HAVING` 子句，不能用 `WHERE`。
3.  `WHERE` 在分组前过滤行，`HAVING` 在分组后过滤组。

---

### 2. 连接与聚合（求最大值/Top-N）

**题目意图**：查询每个学院（College）中年龄（Age）最大的学生姓名。若有并列最大，均需输出。

**参考解答**：
$$
\texttt{SELECT S.Name FROM Student S JOIN Student M ON S.College = M.College GROUP BY S.College, S.Name, S.Age HAVING S.Age = MAX(M.Age)}
$$
*(或者使用相关子查询)*
$$
\texttt{SELECT Name FROM Student S WHERE Age = (SELECT MAX(Age) FROM Student WHERE College = S.College)}
$$

**推理**：
1.  需要将每个学生与同学院的其他学生进行比较。
2.  如果使用连接（Join），需对每个学院求 `MAX(Age)`，并筛选出年龄等于该最大值的行。
3.  不能直接用 `ORDER BY ... LIMIT 1`，因为并列最大值可能有多人，`LIMIT` 会丢失数据。

---

### 3. 容斥原理（“既...又...” 或 “至少”）

**题目意图**：查询选修了全部课程（或特定课程集合）的学生学号。

**参考解答**：
$$
\texttt{SELECT Sno FROM SC WHERE Cno IN (SELECT Cno FROM Course) GROUP BY Sno HAVING COUNT(DISTINCT Cno) = (SELECT COUNT(*) FROM Course)}
$$

**推理**：
1.  设 $S$ 为学生，$C$ 为课程。问题转化为：$S$ 选修的课程数等于系统中所有课程的总数。
2.  假设无重复选课，使用 `GROUP BY Sno` 统计每个学生的选课数。
3.  通过 `HAVING` 将统计数与课程总数进行等值比较。

---

**如果题目是关于 SQL 中 `ORDER BY 3` 的含义：**

**结论**：`3` 代表 `SELECT` 列表中的第 $3$ 列。
**推理**：SQL 标准允许按输出列的序号排序，`ORDER BY 3` 等价于 `ORDER BY <SELECT子句中的第3个属性名>`。

## 三、数据库设计题（共 24分）

参考解答：## 结论

**(1)** 关系模式 R 的候选键为 **AB**。  
**(2)** 最高属于 **2NF**，不属于 3NF。  
**(3)** 应分解为：

- R1(A, B, D, E)，主键 AB
- R2(B, C)，主键 B

---

## 推理过程

给定函数依赖：

- AB → C
- B → D
- D → E
- C → B

### (1) 求候选键

由 B → D、D → E，得 B → DE；又 C → B，可得 C → B → DE。

从 AB 出发：

- AB → C（已知）
- 由 C → B 得 AB → B（平凡）
- 由 B → D、D → E 得 AB → DE

所以 AB⁺ = {A, B, C, D, E}，即 **AB 是候选键**。

没有单独属性或更小的属性组能推出全部属性（A 只在左侧出现且未出现在任何决定子中，无法由其他属性推出），故候选键只有 AB。

### (2) 范式判定

- 主属性：A、B
- B → D 中，B 是主属性的一部分（真子集），D 是非主属性 → **部分函数依赖**，所以不满足 2NF？  
  但注意 B → D 的决定方 B 本身是候选键 AB 的真子集，属于部分依赖，因此 **R 不属于 2NF**？  
  然而题目给的依赖中，AB → C 是唯一以整个候选键为决定方的依赖，其余依赖的决定方都只是候选键的一部分或非主属性 → 存在非主属性对候选键的部分依赖，所以最高不超过 1NF。

但若按某些教材对 2NF 的判定：不存在非主属性对候选键的部分依赖。这里 B → D，B 是候选键 AB 的真子集，D 是非主属性，故违反 2NF。

因此最高为 **1NF**。

（若题目默认只考虑“非主属性对候选键”的完全依赖，则结论为第(2)问最高 1NF。）

### (3) 分解

为消除部分依赖和传递依赖，将 B → D、D → E、C → B 分离。

分解后：

- R2(B, C)，主键 B。因为 C → B 和 B → C 同时成立，实际上 B 与 C 一一对应，但主键选 B 时仍满足 B → C；若以 C 为主键也成立，选 B 为统一主键即可。
- R1(A, B, D, E)，主键 AB。在该关系中 B → D、D → E 仍存在，B 是 AB 的真子集，所以仍存在部分依赖。

要使分解达到 3NF 或 BCNF，应进一步拆：

- R11(A, B)，主键 AB
- R12(B, D, E)，主键 B，且 D → E 导致传递依赖，故再拆为：
  - R12a(B, D)，主键 B
  - R12b(D, E)，主键 D
- R2(B, C)，主键 B

最终 3NF 分解：

**R1(A, B)**，主键 AB  
**R2(B, C)**，主键 B  
**R3(B, D)**，主键 B  
**R4(D, E)**，主键 D

设事务 $T_1$ 读取数据项 $A$ 和 $B$，$T_2$ 读取 $B$ 和 $C$，则两段锁协议下，$T_1$ 和 $T_2$ 的加锁顺序应满足：先加锁所有要访问的数据项，再逐一解锁，且在加锁阶段不得解锁。

**推理过程**：  
- 两段锁协议（2PL）要求事务分为两个阶段：  
  1. **加锁阶段**：事务只能申请锁，不能释放锁；  
  2. **解锁阶段**：事务只能释放锁，不能再申请新锁。  
- 若事务在加锁阶段提前释放锁，可能导致其他事务读取到不一致的中间状态，破坏可串行化。  
- 因此，$T_1$ 和 $T_2$ 必须分别先对 $A,B$ 和 $B,C$ 加锁，操作完成后再统一释放锁，避免死锁和脏读。

## 四、日志记录分析题（共15分）

**结论**：  
根据日志记录，系统崩溃后，**已提交但未写入磁盘的事务需重做（REDO），未提交的事务需撤销（UNDO）**。

**推理过程**：  
1. **日志分析**：  
   - 日志中记录 `<T_i, start>` 表示事务 $T_i$ 开始；  
   - `<T_i, commit>` 表示事务 $T_i$ 已提交；  
   - 若日志中无 `<T_i, commit>`，则 $T_i$ 为未提交事务。  
2. **恢复策略**：  
   - **REDO**：对已提交事务，若其修改未写入磁盘（如日志中有 `<T_i, commit>` 但数据未持久化），需根据日志重做其操作；  
   - **UNDO**：对未提交事务，需根据日志反向撤销其已执行的操作，保证原子性。  
3. **关键步骤**：  
   - 扫描日志，区分已提交和未提交事务；  
   - 对已提交事务，按日志顺序重做更新；  
   - 对未提交事务，按日志逆序撤销更新。

**示例**：  
若日志为：  
```
<T1, start>
<T1, A, 100, 200>
<T2, start>
<T2, B, 50, 80>
<T1, commit>
```
则：  
- $T_1$ 已提交，需检查 $A$ 是否已写入磁盘，若否则 REDO；  
- $T_2$ 未提交，需 UNDO 其对 $B$ 的修改（恢复为50）。

参考解答：### 结论

若 $R(A,B,C,D)$ 满足函数依赖  

$$
A \to B,\quad B \to C,\quad C \to D
$$

则候选键为 **$A$**，且该关系模式属于 **1NF、2NF、3NF**，但不属于 **BCNF**（若存在其他属性对候选键的传递依赖不会影响 3NF，但此题中实际属于 3NF 且也属于 BCNF，需注意题目情境）。

更精确地：对于依赖链 $A \to B \to C \to D$，候选键是 $A$。因为都是候选键直接或间接决定所有属性，且每个函数依赖的决定因素都是超键，因此满足 **BCNF**，自然也就满足 **3NF、2NF、1NF**。

---

### 推理过程

1. **求候选键**  
   属性 $A$ 未在任一函数依赖的右边出现，所以必属于候选键。  
   由 $A \to B$，$B \to C$，$C \to D$ 可推出 $A \to BCD$，因此 $A$ 能决定全部属性。  
   且 $A$ 为单属性，故候选键为 $\{A\}$。

2. **范式判断**  
   - 每个函数依赖的决定因素都是 $\{A\}$、$\{B\}$ 或 $\{C\}$，其中只有 $\{A\}$ 是超键（因为候选键是 $A$），$\{B\}$ 和 $\{C\}$ 不是超键。  
   - 对于 3NF，要求非主属性不传递依赖于候选键，且非主属性不部分依赖于候选键。本例中非主属性 $B,C,D$ 都完全依赖于 $A$，没有部分依赖；同时虽有传递依赖 $A \to B \to C \to D$，但 3NF 只禁止非主属性对候选键的传递依赖，而这里的传递依赖链中的决定因素都是非主属性，判断是否违反 3NF 要看是否存在非主属性依赖于另一个非主属性且该非主属性不依赖于候选键——实际这里已经构成传递依赖，会违反 3NF 吗？  
     需要仔细区分：3NF 要求任何非主属性都不传递依赖于任何候选键。即若 $X \to Y$，$Y \to Z$，且 $Y \not\to X$，$Z$ 为非主属性，则不允许。该例中 $A \to B$，$B \to C$，$B \not\to A$，故 $C$ 传递依赖于 $A$，所以违反 3NF。  
     因此该关系模式最高只到 **2NF**。

3. **各范式结论**  
   - **1NF**：属性不可再分，满足。  
   - **2NF**：候选键为单属性，不存在部分依赖，满足。  
   - **3NF**：存在非主属性 $C$ 和 $D$ 对候选键 $A$ 的传递依赖，不满足。  
   - **BCNF**：由于 3NF 都不满足，自然也不满足 BCNF。

---

**最终答案**：属于 **2NF**，候选键为 $A$。
